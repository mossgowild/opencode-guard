# opencode-guard

English | [简体中文](README.zh-CN.md)

An OpenCode 2 plugin (macOS, OpenCode 2.0.32 or later) that runs OpenCode's shell commands in Claude Code's own sandbox ([sandbox-runtime](https://www.npmjs.com/package/@anthropic-ai/sandbox-runtime)), configured by the `sandbox` section of the plugin's own config file, written like the `sandbox` section of Claude Code's settings; the plugin never reads Claude's settings. Anything beyond the sandbox is left to OpenCode's own `permissions`, which should prompt for it. Two modules that know nothing of each other do this: the sandbox (`src/sandbox`: the first two items below) and auto review (`src/autoreview`: the third); `src/index.ts` wires them together.

- **Sandbox**: every shell command (the model's and the user's) is wrapped by sandbox-runtime with the `sandbox` section, re-read for each command, plus the session's directory as writable and OpenCode's project config in it (`.opencode/`, `opencode.json`, `opencode.jsonc`) as read-only: a project plugin written there would run in later sessions and could replace the sandbox. It also keeps what Claude Code's own sandbox keeps on top of the settings: Claude's configuration in the session's directory and every directory above it up to home (`.claude/settings.json`, `.claude/skills`, `.claude/hooks`, `.mcp.json` and the like) and its state under `~/.claude` are read-only, and the credentials there (`~/.claude/ide`, `seed-admin`, `bridge-spawn`) are unreadable; git hooks and config, shell startup files and the like are read-only as in Claude Code. Without `allowedDomains` in the `network` section the network is unrestricted: no proxy, every connection (SSH and other raw TCP included) is allowed. With it, network goes through sandbox-runtime's proxy: `deniedDomains` are denied, everything else is allowed, and connections that ignore the proxy fail. The plugin swaps the shell for `bin/sandboxed-shell`, a script shipped with it that runs the wrapped command, passed in the environment, so the command stays as written: OpenCode always runs `[shell, "-c", command]`, and its own permission check, the titles of background commands and the notices to the agent all show that command. If no sandbox can be built (no `sandbox` section, invalid settings), the command is refused.
- **Escape**: for a command the sandbox blocks, the shell tool gets two more fields, `unsandboxed` and `explanation`, as Claude Code's Bash has `dangerouslyDisableSandbox`. What the sandbox allows and when to leave it is in the `unsandboxed` field's own description: OpenCode sets the shell tool's description anew for each request, so text added to it never reaches the agent. The plugin adds them to the tool's Effect input with `mapFields`, from existing fields described anew, so they come from OpenCode's own Effect; an input it does not know stays as it is, and the agent then has no way out of the sandbox. OpenCode gives the `execute.before` hook the input as the agent sent it, before it decodes it, so the plugin takes both fields out there and the shell tool never sees them. With `unsandboxed: true` the agent must give an explanation: one or two plain sentences in the user's language that say what the command is for, why it has to run outside the sandbox, and what it writes, deletes, connects to, starts or stops there, or that it is read-only; without one the user is not asked, nothing runs and the call fails saying why. The plugin asks there, not in the shell tool's own permission check, which the shell tool skips for a command it cannot split into commands. It asks as OpenCode's shell does, under the action `shell`, with the command's parts as resources, split by OpenCode's own parser (`ShellParse.scan` from `@opencode/core`, pinned to OpenCode's version, loaded on first use; the whole command is the one part when that finds none or fails, where OpenCode would not ask), and the call's input (`command`, the `workdir` given, `unsandboxed: true`) in `metadata.input` for whatever reviews the request. The plugin's permission hook puts the explanation, as written, into the prompt's message, shown above it. It always asks, whatever the rules say for `shell`: only a rule denying the command denies it, and no session rule skips the question. Who answers is not the sandbox's concern: OpenCode's prompt, or auto review when it is on. The request carries no `save`, so the prompt offers no "always allow". A denial by a rule, or the user declining with a word, fails the call with that message; declined without a word, the call fails with OpenCode's own error, which ends the agent's step, as OpenCode's own prompts do. Once allowed, the command is an ordinary shell call: in the foreground or, with `background`, in the background, listed with OpenCode's other background commands and reported to the agent when it ends; interrupting the session kills it. OpenCode's shell hook sees only a command and its directory, not the call it came from, so the plugin puts a one-time random token on a comment line above the command; the hook runs the command unwrapped only when the token is one the plugin handed out and has not seen used, and removes the line first, so what OpenCode runs, lists and reports is the command without it. The token alone is the pass, not the command: plugins whose `execute.before` hooks come later in the same call may rewrite the command below the line (RTK turns `ls` into `rtk ls`), and only that call's input carries the token. The session keeps the call as the agent sent it. A token is good once; any other command with such a line, forged or replayed, runs sandboxed with the line in it. The tokens handed out are kept for the process, not for one load of the plugin: OpenCode reloads the plugin while calls are in flight, and a token the old load granted is taken by the new one's shell hook.
- **What the sandbox blocked**: after a sandboxed shell call ends, what Seatbelt denied that command goes after its output in a `<sandbox_violations>` block, with a line on how to leave the sandbox, as Claude Code does; the `unsandboxed` field's description says what a sandbox block looks like, to retry with it rather than ask first, and to tell the user instead when what was blocked has nothing to do with the task. The lines are the kernel's own denials, not a guess from the output, less the system queries every command is denied (`sysctl-read`, `system-info`). sandbox-runtime tags each command's denials in the system log with an id the plugin gives it; the plugin reads them with its own `log stream`, one per process, every line, because sandbox-runtime's monitor keeps only the first denial of each chunk the log writes and drops the rest on a busy machine. A shell between the plugin and `log stream` stops it when OpenCode ends, killed outright included. The log usually arrives within 25 ms of the command's exit; a failed command whose output says it was refused something waits up to two seconds for it, other commands do not wait. A command moved to the background is left as it is.
- **Auto review**: when it is on, takes over every permission request that would prompt, the sandbox's included; when it is off, it leaves them all to OpenCode. A model first reviews each in one `generate.text` call, so it works with any model OpenCode lists, `claude-code/…` included. It is a simplified Claude Code local auto-mode classifier: the model decides whether the agent's latest action should be blocked, under the user's rules (`policy`) only, without Claude's default rule tables. It gets the AGENTS.md files (only a clear authorization in them for the same operation on the same target counts), the working and home directories, and the transcript laid out as Claude lays out its own: one JSON line per entry; the user's messages (with the text pasted into them), their answers to the agent's questions (an option they picked with the description it was offered with) and the commands they ran, whole; the agent's prose; each tool call that is not a lookup, with how it ended (`ok`, `error`, `interrupted`, `rejected-by-user`) and without its output; OpenCode's compaction as a summary the agent wrote; the action last. In a subagent's session the parent agent's task counts as the user's message, as in Claude. Unlike Claude's classifier, and as Cursor's does, the model may look at local files before it answers: it answers with lines such as `<read path="tool.sh"/>` (with `offset` and `limit` for part of a long file) or `<list path="."/>`, at most five, and the plugin reads for it and asks again with the results, each cut to about 2,000 tokens and marked as file contents, not the user; three rounds at most, after which a model still looking leaves the request to the user. Paths start from the session's directory, links are resolved first, and nothing the sandbox keeps unreadable (`denyRead`, Claude's credentials) or binary is read: what is read goes to the review model's provider. Non-user lines are cut to about 1,000 tokens and kept newest first within about 20,000. The prompt says how to read the transcript and when the user has consented (their own message names the action and target, or they affirmed the one next step the agent proposed right before). The model answers `<block>yes</block><reason>…</reason>` or `<block>no</block>`; only an unambiguous `no` lets the request through. A call it lets through starts its output with `Auto-approved`. Anything else, a failure or no answer within 60 seconds included, the user answers on a prompt the plugin raises in place of OpenCode's: the same action, resources and details, without `save`, so no prompt offers "always allow" (for an edit OpenCode would save `*`, and later edits anywhere in the project would neither prompt nor be reviewed). The review's reason goes on the prompt on a line of its own as `⚠ Auto review: <reason>`. A permission hook cannot drop `save` from OpenCode's own prompt, so the hook raises its own, waits for the answer and settles the original request by it: allowed once, it goes ahead; declined with a word, it is denied and the words go back to the agent; declined without one, it fails with OpenCode's own error, which ends the agent's step. A key `opencode-guard.stand-in` in the prompt's details marks it as the plugin's own, so it is not reviewed again.
- **Languages**: the plugin's own words for the user (`⚠ Auto review:`, `Auto-approved`) are in English or Chinese (`⚠ 自动审查：`, `已自动放行`), by the environment it runs in: the locale variables `LC_ALL`, `LC_MESSAGES` and `LANG`, unless they are unset or only `C` or `POSIX`, as OpenCode's server often gets; then macOS's preferred language; English otherwise. What the agent and the review model write follows the chat: the tool asks the agent for its explanation in the user's language, and the reviewer gives its reason in the language of the user's messages. Text only models read (tool descriptions, what goes back to the agent, the sandbox's errors) stays English.

## Files

| Path | What |
|---|---|
| `~/.config/opencode/opencode-guard.json` | `sandbox`: as in Claude Code's settings. `autoReview` (optional): see below |

Only the session's own directory is writable as the workspace, not OpenCode's project directory: that is the enclosing git root, which can be far wider.

Load the plugin as a directory in an OpenCode plugin directory, `~/.config/opencode/plugins/opencode-guard/`, with two one-line forwarders: `index.ts` for the server and `tui.tsx` for the terminal.

```js
// index.ts
export { default } from "/Users/<you>/code/opencode-guard/src/index.ts"
// tui.tsx
export { default } from "/Users/<you>/code/opencode-guard/src/tui.tsx"
```

OpenCode's terminal prompt for a shell request shows the command but not the request's message, so the terminal half (`src/tui.tsx`) draws the agent's explanation for leaving the sandbox right above the prompt, in the prompt's colors and edge, until the request is answered. OpenChamber shows the message itself.

`autoReview`, all of it read for each request, so edits apply at once; when it is off, requests prompt as OpenCode's own; when it is on but cannot be used, a request that would prompt goes to the plugin's own prompt without a review:

```json
"autoReview": {
  "enabled": true,
  "model": "magpie/claude/claude-haiku-5-5",
  "policy": ["## The user's write scope", "1. …", "…"]
}
```

`model` is `<provider>/<model ID>` as OpenCode lists it. `variant`, optional, is one of that model's variants (such as `"high"`), as OpenCode's own `variant` beside an agent's `model`; without it the model's default is used. `policy` is the user's rules, one string per line: the reviewer allows what they let go ahead and asks for the rest.

Permission rules that go with it (`permissions` in `opencode.json`), so that only what the sandbox does not cover prompts: allow everything, then ask for edits outside the session's directory (OpenCode gives an edit there as an absolute path). A command run outside the sandbox always asks, without a rule:

```json
[
  { "action": "*", "resource": "*", "effect": "allow" },
  { "action": "edit", "resource": "/*", "effect": "ask" }
]
```

## Tests

`bun test` runs the unit tests; the ones that run the real sandbox are skipped inside another Seatbelt sandbox, since Seatbelt cannot nest. End-to-end checks need an `opencode serve` started outside any other sandbox for the same reason.

To uninstall, remove `~/.config/opencode/opencode-guard.json`, the plugin directory, and those permission rules.
